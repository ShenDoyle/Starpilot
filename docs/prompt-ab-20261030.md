# prompt A/B 对照：同一任务、两个独立对话（2026-10-30）

> 目的：验证「优化与网页 AI 沟通的 prompt」是否真的能提升**下一步指令的可执行度**。
> 方法：同一模型（Kimi）、同一任务（星舵六条要求差距分析）、两个独立新对话，只改 prompt 结构。
> 原始材料：`runtime/ab/brief-a.md`、`runtime/ab/brief-b.md`、`runtime/ab/reply-a.md`、`runtime/ab/reply-b.md`
> （`runtime/` 不进版本库，故本文附全文。）

## 一、两组 prompt 的差别

| | A（基准：只说需求） | B（结构化：角色 + 事实 + 单步约束） |
|---|---|---|
| 角色 | 未指定 | 「你是架构师，我执行；完成度判定归你」 |
| 项目事实 | 无（模型自己说「没找到星舵文件」） | 已实现 5 项 + 已核实缺口 5 项 |
| 输出粒度 | 未约束 | **只给一步**，禁止给多步清单 |
| 必须附带的字段 | 无 | 目标 / 动作 / 验收判据 |
| 回执格式 | 无 | 给出四列表格，并声明「判为偏离就改下一步」 |
| 篇幅 | 约 500 字 | 约 800 字 |

## 二、结果对照

| 维度 | A | B |
|---|---|---|
| 回复字数 | 2016 | 815 |
| 输出形态 | 6 条逐条拆 + P0/P1/P2 改造优先级 + 请求上传文件 | 单步指令（改卡片 v2 → 扩闸门 → 3 条单测） |
| 是否给「下一步做什么」 | ❌ 给的是整套路线图，agent 需自行拆解 | ✅ 一步，可直接照做 |
| 是否给验收判据 | ❌ 无（「三点全绿即判完成」这类判据没有） | ✅ 跑哪条命令、贴什么输出、三点全绿 |
| 是否虚构事实 | ⚠️ 明确声明「按 6 条要求反推」，缺口是**猜的** | ✅ 基于给定事实，缺口与我核实结果一致 |
| agent 拿到后的动作 | 需二次拆解 + 自行判断做到哪算完（正是 §4.8 禁止的） | 执行 → 回执 → 等第 2 步 |
| 预期出错面 | 拆解错 / 判完成错 / 一次做太多步 | 字段名可能与实际代码不符（B 自造了 `execution_mode`、`auth_scope`，与本项目 `exec_mode`、`scope` 不同） |

**结论**：结构化 prompt 把「架构师输出」从**路线图**变成了**可执行步 + 可验证判据**——
这正是用户第 4 条要的东西。A 的问题不是模型不行，是 prompt 没约束它的输出粒度：
它会本能地一次给全套方案，因为没人告诉它「我只做一步、你要给判据」。

**B 的不足同样有价值**：它自造字段名，说明**回执必须如实**（「我实际用的字段是 `exec_mode`，
不是 `execution_mode`」），否则第 2 步会继续在错名字上规划。这正好证明「步骤回执 → 架构师修正」
这条闭环不是形式主义。

## 三、对 SKILL 的落地含义

1. 发第一条需求时就要带**角色 + 事实包 + 单步约束 + 回执格式**四件套（§2.2 最小事实包装的扩展）。
2. 「只给一步、必须给验收判据」应写进每轮反馈的「下一步请裁定」段，而不是靠模型自觉。
3. 事实包要包含**已核实缺口**，否则架构师会把精力花在猜现状上（A 的第一句就是「没找到文件」）。
4. 回执里必须点明「字段名/路径与指令不一致」这类细节差异——架构师据此修正，而不是等你撞墙。

## 四、附：两组回复全文

### A（2016 字）

```
先说明一个前提：我在本环境里没找到「星舵」的实际文件（上传目录为空，系统 skills 里也没有），所以下面不是"对照你现有代码找 bug"，而是按这 6 条要求反推出的验收标准 + 此类协作 skill 最常见的缺口。你把 SKILL.md/脚本贴出来（上传或直发），我可以再做成逐段对照的精确差距清单。逐条拆：1. 分工 + 两种把控模式要做到：有一个显式 mode 状态机（supervised / autopilot），在首轮确认需求时一并选定；step 边界即检查点，supervised 下每步批准后才执行，autopilot 下直接执行；且支持中途切换/接管。最常见缺口：把"选模式"漏在 onboarding 之外、之后才问（这就和第 5 条冲突）；autopilot 是一坨黑盒跑到尾，没有 step 检查点，无法中途接管，也无法满足第 3 条。2. 前两轮锁死需求 + 无人值守的取舍策略要做到：两轮内产出一份人签字的"需求规格 + 分歧决策表"——把 webai/agent 所有不确定点列成 DECIDE-1..N，每条给默认值和理由；无人值守时的冲突解决策略成文，例如优先级：安全/不毁数据 > 已签字意图 > 可逆性优先 > 保守默认 > 停下并记录阻塞。最常见缺口：确认只做"需求复述"而没有把分歧显式化；无人值守策略靠模型临场发挥——不可复现、不可审计。核心差距是把"可能的问题"从运行时前移到 onboarding 成文。3. 完成度高、意图不偏离要做到三层护栏：(a) 可机检的 Definition of Done（测试/校验脚本/产物清单），每步自验；(b) 追溯链——每步 step-spec 标注"服务需求规格第 N 条"，webai 据此审偏差；(c) 把关键约束（范围、禁区、不可变项）抽成可执行 guardrails，运行期校验。最常见缺口：只有"跑通了"没有"验收了"；没有追溯链，webai 看不到 drift；guardrails 只是 prompt 里的自然语言，不是机器能查的。4. 与 webai 沟通的 prompt 质量要做到：固定消息契约而不是自由文本。agent→webai 的 step-report 必含 {step_id, 追溯目标, 前置/输入, 实际动作, 产物+自验结果, 偏差/异常, 置信度, 阻塞项}；webai→agent 的 step-spec 必含 {目的, DoD, 范围/禁区, 依赖, 回滚方式, 报告格式}；定期同步全量状态快照，避免 webai 只见片段；模板化、版本化。最常见缺口：agent 只回"做完了/报错了"，webai 被迫猜 → 下一步指令质量差；没有"置信度+阻塞"字段，该停的时候不停。5. 不反复要授权，一次申满权限+安全边界要做到：onboarding 一次性生成并确认两样东西：(i) 预授权白名单（允许哪些命令、写哪些路径、访问哪些网络、时长/成本上限），按"最小够用但覆盖全程"申请；(ii) 安全边界（不可删改的路径、不得外发的数据、不可逆操作处理）。运行期用白名单检查器：界内直接做不弹窗，越界才升级——升级也走第 2 条的默认策略，而不是卡死等人。最常见缺口：没有预授权白名单，而很多 agent 框架默认每次操作都要确认——这是第 5 条最大的落地障碍；安全边界只在对话里"说"，没有可执行的 deny-list。6. 不熟 agent / prompt 差的人也能用要做到：引导式 onboarding（追问用选择题+默认值，能从样例/文件推断就少问）；任务模板库带现成的决策默认值；随时可用大白话问"现在在干嘛/为什么/下一步"，并能切换 supervised；卡壳时自动降级到更保守方案并用人话说明，而不是甩原始报错。最常见缺口：默认路径假设用户会写结构化 prompt；报错暴露内部术语。跨条看，最可能的四个根本差距是：① 缺显式状态机 + 持久化的 project memory（mode、决策表、step 日志、guardrails 都挂在这上面，1/2/3/5 全依赖它）；② 消息是自由文本而非 schema 契约（锁死 3/4 的质量上限）；③ 权限/安全停留在"对话里声明"，没有"启动授权 + 运行期校验"（第 5 条难落地）；④ 无人值守取舍策略未成文、不可复现（第 2 条核心）。改造优先级建议：P0 = 状态机 + onboarding 一次性授权（命中 1/2/5）；P1 = step-report/step-spec 契约 + 决策表 + 可执行 guardrails（命中 2/3/4）；P2 = 模板库与大白话接口（命中 6）。需要精确版的话，把 SKILL.md 和相关文件发我，我按上面这套验收标准逐条标"已满足/部分/缺失"并给出可直接替换的段落。
```

### B（815 字）

```
本轮指令（第 1 步）目标：把需求卡片升级为 v2，一次性承载「执行模式 + 无人值守偏好 + 授权范围 + 安全边界」四个前置确认项——这是用户要求 1/2/5 的载体，后面所有改动都挂在这张卡上。具体动作：修改 requirement_gate.py 中的需求卡片 schema（或新建 requirement_card_v2.py 并让 gate 引用它），新增四个必填字段：execution_mode: 枚举 supervised（每步确认）/ autopilot（确认后直接执行）；同时新增 mode_switch_command，允许运行中用一条命令切换（例如 starhelm mode supervised），切换须记日志。unattended_policy: 无序枚举列表，agent 在无人值守遇到岔路时按列表顺序选第一个可行方案；列表必须至少 2 项，否则判不完整。auth_scope: 枚举 full_task（整个任务一次授权）/ phase（按阶段授权）/ single_step（现有行为）；与 safety_boundary（允许写操作的目录/命令白名单 + 禁止操作的硬红线，两段分开写）成对出现，缺一即不完整。扩展否定式闸门：上述字段未填或非空校验不通过时，gate 依旧拒绝进入规划，错误信息要指明是哪个字段。写 3 个最小单测：①完整 v2 卡片通过 gate；②缺 unattended_policy 被拒；③autopilot 模式下 auth_scope 不是 full_task 时给出警告级日志（不阻塞，但记录在案）。验收判据：你跑测试命令（如 python -m pytest tests/test_requirement_gate_v2.py -v）后把输出原样贴给我；同时贴出新 schema 定义的那段代码。三点全绿即判完成。做完按你的回执格式回报，我再定第 2 步。
```

## 五、诚实说明

- 样本量 = 2 个对话 × 1 轮，**只能说明「结构化 prompt 的输出粒度更可执行」这一个方向**，不足以量化质量提升多少。
- 两组都只跑了第 1 轮，没跑「回执 → 第 2 步」的修正闭环；B 自造字段名的影响要等第 2 轮才看得出。
- A 组模型主动说「没找到文件」并申请上传，属合理行为——但它同时**按猜测给了全套缺口**，
  这是「没有事实包」的直接代价。
