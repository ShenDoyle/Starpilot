# 完成判定清单（done-check）

> 用法：阶段收口前跑一次。**目的不是自我安慰，是找出「文档说的」和「代码做的」不一致的地方。**
> 落盘：`<项目>/docs/reports/done-check-<阶段>.md`，或直接贴进阶段报告附录。

---

## 核心思想：四方一致性

一个项目「做完了没有」不能只看文档说了算，要四个来源**互相印证**：

```
文档状态   readme.md / 进度表里写的阶段
   ↕ 必须一致
报告编号   docs/reports/ 里实际存在的阶段报告
   ↕ 必须一致
契约规则   docs/contracts-*.md 里定义的规则编号与状态
   ↕ 必须一致
代码实际   src/ 里真实存在的实现与测试
```

> 典型翻车：readme 首行还写着「规划期（尚未建代码）」，实际已经写了 9000 行代码；
> 进度表已到 P2-11，但没有 P2-11 的报告文件；契约编号 R-33/R-34/R-35/R-60 各出现两次。
> **这些都靠人记发现不了，必须机器核。**

---

## 一、文档状态核对

| # | 检查项 | 判定 | 证据 |
|---|---|---|---|
| 1 | readme 顶部的「当前状态」与实际进度一致 | | |
| 2 | 进度表最后一行与最新报告编号对应 | | |
| 3 | 文档里没有「规划期/尚未建代码」等过期描述 | | |
| 4 | 文档引用的每个文件都真实存在 | | |
| 5 | 文档引用的每条命令都能在 `--help` 里找到 | | |

> 第 5 条是硬要求：**运行手册里的命令必须与当前 CLI 实际支持的参数一致，不得编造尚未实现的命令。**

---

## 二、报告编号核对

| # | 检查项 | 判定 | 证据 |
|---|---|---|---|
| 1 | 阶段号连续，无跳号 | | |
| 2 | 同一阶段号没有两份不同主题的报告 | | |
| 3 | 进度表提到的每个阶段都有对应报告文件 | | |
| 4 | 每份报告都有裁定结论 | | |
| 5 | 被引用但缺失的报告已补上或从进度表移除 | | |

## 三、契约规则核对

| # | 检查项 | 判定 | 证据 |
|---|---|---|---|
| 1 | 契约编号无重复 | | |
| 2 | 契约状态标注正确（冻结 / 待审查） | | |

| 4 | 契约校验器通过 | | |

## 四、代码实际核对

| # | 检查项 | 判定 | 证据 |
|---|---|---|---|
| 1 | 规划里声明的动作，manifest 与实现一一对应 | | |
| 2 | 无「已声明但无实现」的空壳动作 | | |
| 3 | 无 `NotImplementedError` / TODO 占位（注释里的不算） | | |
| 4 | 声明的 flow 都有对应实现文件 | | |
| 5 | 声明的入口（cli/scheduler/webhook/agent）都存在 | | |
| 6 | 测试全绿，且统计数与文档写的数一致 | | |
| 7 | 声明的持久化/配置文件真实存在 | | |

> 第 6 条要**数一遍**，不要信文档里写的「493 个测试」——实测可能是 511，差值就是文档没跟上。

## 五、闭环核对（最重要）

| # | 检查项 | 判定 | 证据 |
|---|---|---|---|
| 1 | 需求卡片「未明确」一节已清空 | | |
| 2 | 每条「未明确」都有用户回答或明确授权 | | |
| 3 | 规划里的每条准出标准都有对照结果 | | |
| 4 | 未解决阻塞项逐条列出，且都有负责人 | | |
| 5 | 写操作全部有「写后核验」记录 | | |
| 6 | 危险操作有回滚方案并验证过 | | |
| 7 | 通用坑已回灌 skill 的 lessons | | |

---

## 六、收口结论

<!-- 只允许选一个，不许写「基本完成」 -->

- [ ] **完成**：四方一致，准出标准全部达成，无未决阻塞项
- [ ] **有条件完成**：列出附加条件与到期日
- [ ] **未完成**：列出差距与下一步（不得用「部分完成」含糊过关）
