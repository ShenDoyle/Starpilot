# 反馈与失败转交模板

> 用法：每轮执行完发给网页版 AI 的内容。**固定七段，缺段视为不合格反馈。**
> 落盘：`<项目>/runtime/wa/feedback-<n>.md`（发出去的原样留档）

---

## A. 常规反馈（每轮结束必发）

```markdown
## 第 N 轮执行结果

**状态**：完成 / 部分完成 / 失败 / 阻塞待裁定

**做了什么**
- （一行一件事，动宾结构）

**步骤回执（逐条对账，不许合并、不许只写「已完成」）**
| # | 它让我做的 | 我实际做的 | 一致？ | 差异原因 |
|---|---|---|---|---|
| 1 | （指令原文摘要） | （实际动作 + 产物路径） | ✅ / ⚠️ / ❌ | （⚠️❌ 必填） |

**证据**
- 命令：`<原样复制>`
- 输出：（关键行原文，不要概括）
- 文件：`<路径>`

**数据**
| 项 | 值 | 出处 |
|---|---|---|

**问题 / 偏差**
- 无 / 具体偏差

**下一步请裁定**
- 只列真正需要它决定的点；不需要裁定就写「无」
```

> **「步骤回执」为什么必须有**：网页版 AI 看不到你的屏幕，它判断「这一步做成了什么样」
> 全靠这张表。只写「已完成」它就会默认「全部按原样执行」，下一轮在错误前提上规划——
> 错误会被滚雪球放大。⚠️/❌ 行必须写清差在哪，它才能改方案。

### 反例（禁止）

- 「已完成，测试通过」——没有证据
- 「应该没问题了」——推测
- 「我也顺便优化了 X」——超范围
- 把报错改写成「有点小问题」——失真
- 「看起来没问题」「应该可以」——无证据结论
- 步骤回执合并成一行、或全部打 ✅ 但没有产物路径——等于没报

## B. 连续两次失败，请求裁定

> 触发条件：同一目标第 1 次失败 → 换一种**同类**方法再试；第 2 次失败 → **停止，禁止再试第三种**。

```markdown
## 连续两次失败，请求裁定

**目标**：（原本要达成什么）

**现象**
```
（完整报错原文，不概括）
```

**已试**
1. （方法一）→ （结果）
2. （方法二）→ （结果）

**我的怀疑**
- （技术层面）
- （**也包括：怀疑指令本身有问题，理由是……**）

**请裁定**
- 是继续换方法，还是这条指令的前提就有问题？
```

> 第 2 条「怀疑指令本身有问题」是**必须写的可能性**。不写等于默认指令一定对。
> 连续硬试会把「指令错误」变成「一堆废墟」，事后无法分辨。

**例外**：明确属于环境瞬时故障（网络抖动、进程被占用）可重试第 3 次，但要在反馈里写明这是瞬时故障重试。

## C. 阶段收口反馈（阶段完成时发）

```markdown
## 阶段 <编号> 收口

**状态**：完成 / 部分完成 / 未达准出条件

**准出标准对照**
| 标准 | 结果 | 证据 |
|---|---|---|

**做了什么**
- （本阶段全部产出，逐条）

**证据**
- 命令 / 输出 / 文件路径

**未解决阻塞项**
1. （逐条列，不许用「基本完成」糊过去）

**超出原定范围的地方**
- （有就写，没有写「无」）

**下一阶段请裁定**
- （只列真正需要它决定的点）
```

## D. 写操作完成后的如实回报

> 写动作（改数据、提交、发通知）**必须**带这一段，不能只报「成功」。

```markdown
## 写操作回报

**动作**：（做了什么写操作）

**dry-run 结果**：（先看命中了什么）

**实际提交**：（提交了什么，条数）

**写后核验**：（怎么验的，验出结果）
- （例：写后重读实时状态，读到 X，与预期一致 / 不一致）

**影响范围**：（涉及哪些单号/账号/群）

**能否回滚**：（能 / 不能，怎么回滚）
```

> 「写后核验」和「能否回滚」为空 = 这次写操作不合规。
> 规则出处：总纲 §七「每一步可回滚」、契约 R-51~R-58。
