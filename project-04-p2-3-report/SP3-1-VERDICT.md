## 二、§9 三项正式裁定

### 9.1 supersedes 两段式语义 —— **正式批准**

接受「旧裁决仍占槽位 → 禁止 supersede → 人工显式撤销 → 退出槽位 → 创建新裁决 →
证据封存 → 进入可消费槽位」的设计。

**明确不批准 `decide()` 自动撤销旧裁决。** 理由：

1. 撤销是独立的治理行为，不应隐藏在创建新裁决的副作用中。
2. 自动撤销会扩大 `decide()` 的权限范围。
3. 两段式操作保留了明确的审计记录。
4. 失败时更容易定位究竟是撤销失败还是新裁决创建失败。

正式冻结：**supersedes 必须先显式撤销旧裁决，再建立替代关系。**

强调：**撤销不等于解锁**。旧裁决撤销后，原 action 仍受 UNKNOWN 安全状态约束，
直到新裁决通过消费验证。

### 9.2 `_adj_hash` 是否纳入 seq —— **维持原规范，不纳入**

继续使用 `type ‖ 0x1F ‖ NFC(trim(locator)) ‖ 0x1F ‖ str(ms) ‖ 0x1E`，前缀 `adj-v1`。

理由：seq 是存储与排序字段；证据行不可改不可删；封存前才允许新增；封存后集合固定。

**正式保留的实现要求**：哈希计算必须**按 seq 确定性排序**（当前实现
`sorted(rows, key=lambda r: int(r[0]))` 已满足）。未来若改变编码规则、字段顺序或
摘要输入范围，**必须升级算法版本，不得静默修改 `adj-v1`**。

### 9.3 两条阶段守卫调整 —— **正式批准**

- G6-HOTFIX：由「断言裁决表不存在」改为「裁决表存在时 G6 仍拒绝两种 UNKNOWN
  unlock 形态」——合理阶段演进，安全目标未降低。
- SP1-A：SP2 符号继续禁止；SP3 只允许三个公开入口、各恰好一处定义；
  **`commit_outcome` 不得读取裁决表或调用裁决 API** ——「第四项必须长期保留」。

## 三、架构评价（要点）

五段链：证据建立 → 人工裁决 → 证据封存 → 消费验证 → 原子解锁。**认可该架构。**

必须坚持的限制：

> 证据裁决只能解决执行结果的认定与本地锁的解除，**不能证明外部副作用只发生了一次**。
> 特别是 `DECIDED_NOT_SENT`，必须有足够的外部证据证明没有发生发送，
> 不能因为没有找到发送成功记录就推断没有发送。这与 SP1-C 冻结的接管原则一致。
