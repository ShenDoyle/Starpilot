## 三、开发流程总览（人机协作版）

所有任务遵循以下线性阶段，**每阶段由负责人审核批准后，Claw 方可进入下一阶段**。

```mermaid
graph LR
A[需求澄清] --> B[方案设计] --> C[编码与自测] --> D[验收测试] --> E[部署上线] --> F[维护迭代]
```

若采用敏捷迭代，每个 Sprint 内部同样走此微观流程。
> ⚠️ **每次任务前置确认**：Claw 接到任何任务后，第一步不是动手，而是声明「本任务处于六阶段中的哪一阶段 + 该阶段准入是否达成 + 产出将落入哪个目录」，对照第十一章红线自检通过后，方可执行。

## 四、各阶段详细流程与准入/准出标准

### 1. 需求澄清阶段
- **输入**：负责人给出的初始需求描述、用户故事或功能点。
- **活动**：
  - Claw 解析需求，输出《需求理解确认单》。
  - 确认单必须包含：结构化需求列表、模糊点提问、边界与异常流程分析、建议的量化验收标准。
- **输出**：经双方确认的**基线需求文档**（存入 `docs/requirements/`）。
- **准出标准**：负责人明确回复“需求确认”，并附最终验收标准。Claw 存档基线。

### 2. 方案设计阶段
- **输入**：已确认的需求文档，以及负责人给出的技术约束（语言、框架、数据库等）。
- **活动**：
  - Claw 输出《技术方案设计书》（存入 `docs/design/`），至少包含：
    - 模块拆解与职责
    - 核心接口定义（请求/响应、错误码）
    - 数据库 E-R 图或表结构（mermaid）
    - 关键时序图或流程图（mermaid）
    - 配置项与第三方依赖
    - 风险点与应对建议
  - 负责人审核方案，提出修改意见。
- **输出**：经过修订的《技术方案设计书》。
- **准出标准**：负责人明确回复“方案批准”，该方案即成为编码的唯一契约。

### 3. 编码与自测阶段
- **输入**：批准的设计方案，负责人下达的分模块开发指令。
- **活动**：
  - Claw 按《协作工程结构标准》在指定目录创建代码。
  - 严格遵循分支命名，提交信息格式 `type(scope): subject`。
  - 为核心逻辑编写单元测试，确保通过。
  - 若接口有变，实时更新 `docs/design/api/` 下的文档。
  - 模块完成后，输出《提测说明》，包含：功能清单、自测结果、环境依赖、配置变更。
- **输出**：通过自测的代码、单元测试报告、提测说明。
- **准出标准（提测标准）**：代码已推送至指定分支；构建成功；核心流程无阻塞 bug；提测说明完整。负责人确认后进入测试。

### 4. 验收测试阶段
- **输入**：提测代码与提测说明。
- **活动**：
  - 负责人依据验收标准进行功能验证，或审查 Claw 生成的自动化测试结果。
  - 发现问题以 `[Bug]` 格式反馈，Claw 先回复“原因分析与修复计划”，负责人同意后再修改。
  - 修改后提供差异说明与回归建议。
- **输出**：Claw 生成的《测试报告》（覆盖范围、执行结果、已知遗留问题）。
- **准出标准（发布标准）**：验收标准全部满足；P0/P1 问题关闭；负责人明确“验收通过”。

### 5. 部署上线阶段
- **输入**：验收通过的版本、负责人指定的部署环境与策略。
- **活动**：
  - Claw 更新 `deploy/` 下的部署配置（Dockerfile、K8s manifests 等）。
  - 输出部署说明（环境变量、初始化步骤、回滚方案）和线上验证清单。
- **输出**：就绪的部署配置与上线文档。
- **准出标准**：负责人执行部署后，按验证清单确认上线成功；Claw 打 Tag 并归档版本。

### 6. 维护迭代
- **活动**：线上问题反馈或新需求提出，重新进入阶段一，形成闭环。
- **要求**：所有热修复也需走简化但完整的流程，并同步更新设计文档。

## 五、协作工程结构标准

> 本节定义了 Claw 执行开发时必须遵守的项目目录与文件组织规则。所有文件的创建、修改、归档均以此为据。

### 5.1 核心原则
1. **单仓管理**：一个项目仅维护一个 Git 仓库，杜绝多文件夹副本。
2. **文档代码一体**：设计文档、接口规范存放于 `docs/`，随代码版本化。
3. **产物不入库**：编译输出、依赖包、日志等必须在 `.gitignore` 中排除。
4. **路径即语义**：目录名即模块名，Claw 通过路径即可理解项目骨架。

### 5.2 标准目录结构

```text
project-root/
├── src/                        # 源代码根目录
│   ├── main/                   # 主程序代码
│   │   ├── controllers/        # 接口层 / 控制器
│   │   ├── services/           # 业务逻辑层
│   │   ├── models/             # 数据模型 / 实体
│   │   ├── repositories/       # 数据访问层 (如适用)
│   │   ├── utils/              # 通用工具函数
│   │   ├── config/             # 应用配置加载
│   │   └── middleware/         # 中间件
│   ├── test/                   # 测试代码
│   │   ├── unit/               # 单元测试
│   │   ├── integration/        # 集成测试
│   │   └── fixtures/           # 测试夹具
│   └── resources/              # 静态资源、模板等
│
├── docs/                       # 项目文档
│   ├── requirements/           # 需求文档、验收标准
│   ├── design/                 # 技术方案、架构图、API设计
│   │   └── api/                # 接口规范 (OpenAPI/Swagger 文件)
│   ├── guides/                 # 本总纲、编码规范、环境搭建说明
│   └── changelog/              # 版本变更记录
│
├── scripts/                    # 辅助脚本
├── deploy/                     # 部署与基础设施配置
│   ├── docker/                 # Dockerfile 及相关
│   ├── kubernetes/             # k8s manifests
│   └── ci/                     # CI/CD 流水线定义
│
├── .gitignore
├── README.md                   # 项目总览、快速启动、Claw指令示例
├── CHANGELOG.md                # 面向用户的版本摘要
└── LICENSE
```

### 5.3 目录职责与约束
- **`src/`**：代码唯一存放地，分层清晰，禁止跨层调用。
- **`docs/`**：项目知识库。Claw 产出的需求确认单、设计书、接口规范必须落在此处。文件命名：`模块_文档标题.md` 或 `日期_标题.md`。
- **`scripts/`**：辅助脚本，每个脚本头部须注释用途。
- **`deploy/`**：部署描述，不含密钥。Claw 在提测/发布时同步更新。
- **`README.md`**：必须包含项目简介、环境要求、启动命令、Claw 协作指令示例。
- **`CHANGELOG.md`**：遵循 Keep a Changelog 格式，由 Claw 维护。

### 5.4 Git 管理与版本标记

| 事项 | 标准 |
|------|------|
| 纯净版初始态 | 仓库第一次提交，或从模板仓库创建。**禁止保留纯净版文件夹副本。** |
| 分支命名 | `feature/模块-功能`、`bugfix/问题`、`hotfix/描述`。 |
| 版本发布 | 使用 `git tag vx.y.z`，并创建 Release，附构建产物链接。 |
| 旧版本归档 | 通过 Git 历史回溯，不保留物理备份文件夹。 |
| 忽略文件 | `.gitignore` 必须包含：`dist/`、`build/`、`node_modules/`、`.env.local`、IDE配置等。 |

## 六、Claw 执行关键支撑规范

### 6.1 代码提交规范
- 提交信息格式：`<type>(<scope>): <subject>`，如 `feat(auth): 实现jwt登录`。
- 单次提交保持原子性。
- 禁止提交本地配置、密钥、编译产物。

### 6.2 代码质量红线
- 必须通过负责人指定的 Lint 规则。
- 复杂逻辑需添加注释或拆分。
- 所有公共方法必须有文档注释。
- 任何巧妙但晦涩的写法必须附加书面解释。

### 6.3 文档即代码
- 接口定义使用 OpenAPI/Swagger，在 `docs/design/api/` 维护。
- 架构图、流程图使用 mermaid 嵌入 Markdown，确保可版本管理。
- 功能变更必须同步更新对应设计文档。

### 6.4 未明确不执行
遇到需求中的二义性、缺失的异常处理、未声明的配置，Claw **必须**以提问列表形式提交，获得负责人明确回复后方可继续。

### 6.5 变更管理
- **轻微调整**：负责人直接反馈，Claw 评估影响后修改，更新相关文档。
- **重大变更**（影响工期或架构）：Claw 先提交变更分析，经负责人确认后，更新需求文档与设计方案，重新排期。

### 6.6 交互指令格式建议
为提升指令清晰度，负责人可使用固定格式：
```
[任务类型]：需求澄清 / 方案设计 / 开发 / 修Bug
[模块]：xxx
[具体描述]：....
[验收标准]：1. ... 2. ...
[关联文档]：链接或上下文
```
Claw 必须以结构化形式回复，先给出“理解概要”，再按要求产出具体交付物。

### 11.1 工程目录绑定（路径即语义）

| 目录 | 角色 | 阶段归属 | 责任人 | 说明 / 准入 |

### 11.6 模板制作标准工作流（七步法）

> 本章定义本工程**每次模板任务的完整执行闭环**。Claw 接到模板制作/迁移/修改任务后，**必须严格按以下七步顺序执行**，不得跳步、不得并行压缩步骤。每一步的产出物须落盘至对应目录，确保可追溯。

- **准入**：未读完 `05-docs/` 核心文档不得进入下一步。
- **对应总纲**：11.2 前置确认 + 11.3 红线自检。

- **动作**：在 `01-source/` 中找到本次需要处理的模板目录（如 `lxj/`）。
- **产出**：确定源路径（如 `01-source/lxj/`）。
- **约束**：**只读核查**——此步骤仅定位与观察，不修改 `01-source/` 内任何文件（守 R12）。
- **异常处理**：若 `01-source/` 中无匹配模板 → 向负责人提问确认源材料，不得自行从外部拉取。

#### 第三步：复制到工作区、初始化工作文件夹（入槽）

- **动作**：将源模板完整复制到 `02-wip/<模板名>/`；在该文件夹内创建本次任务的工作文件（**一律用子文件夹收纳，禁止散落根目录**）：
  - `_验证文档/` —— 放 `<模板名>-核查日志.md`（记录"查了什么、发现了什么、负责人裁决"）与 `<模板名>-测试问题追踪.md`（结构化追踪表：编号 / 文件:行 / 问题 / 方案 / 风险 / 检查方法 / 状态 / 反馈闭环）；

  - 后续修改记录、中间产物均留在 `02-wip/<模板名>/` 内。
- **原则（R14）**：**每个模板的所有工作信息封闭在其自身文件夹内**，不散落到 `02-wip/` 根目录或其他模板文件夹；不使用共享状态桶混合多模板。
- **产出**：`02-wip/<模板名>/` = 可编辑的工作副本（`html/ static/`）+ 工作文档（`_验证文档/`）+ 工具（`_tools/`）。

#### 第四步：全面摸排、整理问题清单（诊断）

- **动作**：通读副本全部 HTML / CSS / JS 文件，对照 `05-docs/` 技术文档逐项核查：
  - 标签语法是否正确（字段是否存在、参数是否合法）；
  - 资源引用是否完整（无 404、路径一致）；
  - 字符集 / 编码 / 语言残留（英文占位符、乱码风险）；
  - GEO / SEO 结构（JSON-LD、meta、语义标签）；
  - 硬编码值（域名、绝对路径、scode 写死）；
  - **资源与性能诊断（每模板必做，细则见 ④.1）**：未引用资源、性能瓶颈、外链资源本地化。
- **产出**：问题清单（分 🔴必须修 / 🟡应修 / 🟢打磨），写入 `<模板名>-测试问题追踪.md`。
- **交互**：问题清单须提交负责人确认优先级与修法后再动手改（守 R1 未明确不执行）。

##### ④.1 资源与性能专项诊断（每模板必做）

在第四步摸排中，除功能 / 标签 / 结构核查外，**必须**对资源与加载性能做专项诊断，结论进入第五步修改清单（守 R1，本步只列项、不执行删除 / 下载）：

1. **未引用资源清理**：扫描 `html/`（含 `comm/` 公共片段）与 `static/css/*.css` 中实际引用的图片 / 字体 / 媒体路径，与 `static/` 目录实际文件做差集，列出**从未被任何文件引用**的多余文件（如未使用的 `blog_*-1.jpg`、`static/file/` 冗余图、孤立字体）；建议删除或移入 `_unused/` 待确认（守 R9：删除须负责人授权）。
2. **页面性能优化**：定位拖慢因素——过大未压缩的图片、阻塞渲染的同步 JS / CSS、请求数过多的第三方库、重复引入的同名资源；给出压缩 / 合并 / 延迟加载（`defer` / `async` / 懒加载）建议，目标缓解「页面速度慢」。
3. **网络资源本地化**：检索 `html/` 与 `css/` 中 `http://`、`https://` 外链引用的资源（图片、字体、JS、CSS、第三方 SDK），列出需**下载到 `static/` 改成本地引用**的清单（规避混合内容告警、外网依赖与跨域，提速且离线可用）；下载后替换原外链，并留存来源备注。

> 说明：以上三项在第四步仅**诊断 + 列清单**；实际「删除多余文件 / 下载外链 / 改本地引用」在第五步执行，性能是否达标在第六步自检复核。

##### ④.2 CSS / JS 合并的强制前置检查（血泪条款）

凡涉及「合并多个 CSS / JS 以减少请求数」，第五步动手前**必须**逐条核对下列 5 点，任一未核对即视为违规操作（守 R7 准出门禁）：

1. **`@import` 陷阱（最高危）**：合并前先 grep 各 CSS 内的 `@import`。CSS 规范要求 `@import` 必须位于文件**最前部**（仅 `@charset`/`@layer` 可在其前），一旦拼接后落到文件中部，浏览器会**静默忽略**该行——典型后果是字体全丢却毫无报错。处理方式：把被 import 的文件**原位内联**替换掉该 `@import` 语句。
2. **相对路径归位**：CSS 内 `url(../font/x.woff2)` 等相对路径以**文件自身位置**为基准。合并输出文件必须放在**与源 CSS 同一目录**（如同为 `static/css/`），否则所有相对路径集体 404。
3. **层叠顺序不可变**：必须严格按原 `<link>` 顺序拼接。典型错误是把 `responsive.css` 排到 `style.css` 之前 → 移动端断点全部被覆盖失效。
4. **压缩须做结构校验**：正则暴力压缩会误伤 `content:"\eXXX"` 图标转义、`url(data:image/svg+xml,...)` 内联 SVG、字符串内的 `/*`。压缩器须用状态机区分 字符串 / url() / 注释；压缩后**必须比对** `{`、`}`、`url(`、`@media`、`@keyframes`、`@font-face` 六项计数与源一致，不一致则**不写盘**。
5. **保留回滚兜底**：原始分体 CSS **不删除**（未被引用的文件不产生任何请求，零性能损失），并在 HTML 引用处写明回滚方法。合并动作必须落在**可重跑的脚本**（如 `02-wip/<模板名>/_tools/merge_css.py`）里，禁止手改合并产物。

> **JS 不同于 CSS**：若 JS 已集中在 `foot.html` 页面底部，本身即不阻塞首屏渲染，**不要为了「加 defer」而动它**——jQuery 插件普遍依赖同步执行顺序，加 `defer` 收益极小、破坏风险极大（守 11.5.3「首要不出错」）。仅 `<head>` 内的第三方统计/推送脚本值得改 `async`。

#### 第五步：按确认方案逐项修改（实施）

- **动作**：依据第四步经负责人确认的问题清单与修复方案，在 `02-wip/<模板名>/` 副本上逐项修改。
- **约束**：
  - 每修一项，在追踪表内更新状态（进行中 → 待验证 → 已验证）；
  - 修改**仅在 `02-wip/` 内执行**，绝不回写 `01-source/`（守 R12）；
  - 若修改过程中发现新问题 → 追加到追踪表、先确认再改（不擅自扩展范围）。
- **产出**：逐步更新的副本文件 + 实时状态追踪表。

#### 第六步：全面检查（自检）

- **动作**：修改完成后，对 `02-wip/<模板名>/` 执行全面检查：
  - 对照追踪表逐项验证每条修复是否生效；
  - 回归检查：确认修改未引入新问题（未破坏原有功能、未产生新的乱码/404/标签错误）；
  - 对照 G0–G4 + N1–N7 准出门禁（守 R7）。
- **产出**：《自检报告》（附在追踪表内或独立文件），标明每项通过/失败。
- **结果判定**：
  - **全部通过** → 进入第七步（交付确认）；
  - **有失败项** → 回退第五步修补，循环直至自检全过。

#### 第七步：交付确认与版本归档（收口）

- **动作 A（自检全过时）**：向负责人汇报自检结果，请求验收确认。
  - **负责人确认「完成」**：
    1. 从 `02-wip/<模板名>/` 整理出**干净的成品文件目录**（剔除工作文档、临时脚本、中间产物，仅留可部署的模板文件 + 追踪表/核查日志等验证文本）；
    2. 复制成品到 `03-delivered/<模板名>/`；
    3. **版本管理**：若 `03-delivered/<模板名>/` 已存在旧版，将其轮转为 `<模板名>-v1`（上一版），**最多保留 2 个版本**（当前版 `<模板名>/` + 上一版 `<模板名>-v1/`）；更早版本删除；
       - ⚠️ **Windows 实操坑**：Python `os.rename()` 重命名非空目录常报 `PermissionError: [WinError 5]`，改用 PowerShell `Move-Item -LiteralPath ... -Destination ... -Force` 完成轮转；轮转脚本须写成「当前版存在才轮转」，避免重跑时误删上一版。
       - 交付脚本（如 `02-wip/<模板名>/_tools/deliver.py`）应把**第六步自检**内置为交付前置门禁：自检项全过才复制；仅「已登记待决项」可豁免放行，其余失败一律终止交付。
    4. 更新 `02-wip/` 内追踪表的最终状态为「✅ 已交付 v<日期>」。
  - **负责人确认「需继续修改」**：
    1. 回退到第五步，在 `02-wip/<模板名>/` 继续修改并记录；
    2. 重复第五步→第六步→第七步，直至负责人确认完成。
- **产出**：`03-delivered/` 内的成品模板（含验证文本）+ `02-wip/` 内完整的修改历史。

```
    ↓
② 定位 01-source/ 中的源模板（只读）
    ↓
③ 复制到 02-wip/<模板名>/ + 初始化工作文档
    ↓
④ 全面摸排 → 问题清单 → 负责人确认

⑤ 逐项修改（仅在 02-wip/ 内）

```
