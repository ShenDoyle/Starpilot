# 协议：状态、反馈、上下文

## 1. state 文件结构

`<工作区>/.wa-state.json`

```json
{
  "url": "https://chatgpt.com/c/<uuid>",
  "session": "abcd",
  "bound_at": "2026-10-28 10:00:00",
  "turn": 7,
  "last_send_hash": "9f2c1a3b7d4e5f60",
  "last_send_at": "2026-10-28 10:42:11",
  "awaiting_reply": false,
  "fail_streak": 0,
  "history": [
    { "turn": 7, "at": "2026-10-28 10:42:11", "hash": "9f2c1a3b7d4e5f60", "chars": 1832 }
  ]
}
```

| 字段 | 作用 | 何时必须检查 |
|---|---|---|
| `url` | 绑定对话，防串台 | 每次发送前 |
| `session` | bsk session id | 每次操作（失效会自动重建） |
| `turn` | 轮次 | 落盘文件命名 |
| `last_send_hash` | 上一轮正文指纹 | 防重复发送 |
| `awaiting_reply` | 已发但未确认回复完成 | **发送前必须为 false** |
| `fail_streak` | 连续失败次数 | ≥2 触发 `replan`：打包失败现场回网页版 AI 换方案（不是停下来找人） |

`fail_streak` 的维护规则：**失败 +1，成功清零**。不要手动改小。

### 1.1 旁挂文件：`<state>.progress.json`

`awaiting_reply` 只回答「在不在等」，不回答「等了多久、卡在哪」。后两个问题由这个
观察文件回答（`wa.py wait` / `triage` 每次探测刷新）：

```json
{
  "stage": "generating",
  "started_at": 1793365528.5,
  "probe_at": 1793365536.0,
  "progress_at": 1793365536.0,
  "seen": {"msg_count": 2, "reply_count": 1, "last_len": 70,
           "doc_len": 1276, "doc_nodes": 1502, "generating": false}
}
```

- `stage`：`waiting` / `generating` / `settling` / `done` / `timeout` /
  `probe_failed` / `session_lost` / 各分诊码（`risk_control` 等）。
- `progress_at` **只在页面真的变了**的时候推进；`probe_at` 每次都推进。
  两者一对照就能分清「探测在跑但页面不动」和「连探测都没在跑」。
- 它不持锁、写失败不影响主流程：**给旁观者看的事实**，不是状态机的一部分。

## 2. 反馈格式（发给网页版 AI）

固定六段，缺段视为不合格反馈：

```markdown
## 第 N 轮执行结果

**状态**：完成 / 部分完成 / 失败 / 阻塞待裁定

**做了什么**
- 一行一件事，动宾结构

**证据**
- 命令：`<原样复制>`
- 输出：（关键行原文，不要概括）
- 文件：`<路径>`

**数据**
| 项 | 值 | 出处 |
|---|---|---|

**问题 / 偏差**
- 无 / 具体偏差

**下一步请裁定**
- 只列真正需要它决定的点；不需要裁定就写「无」
```

### 反例（禁止）

- 「已完成，测试通过」——没有证据
- 「应该没问题了」——推测
- 「我也顺便优化了 X」——超范围
- 把报错改写成「有点小问题」——失真

## 3. 失败转交模板（第 2 次失败时用）

```markdown
## 连续两次失败，请求裁定

**目标**：<原本要达成什么>

**现象**
```
<完整报错原文>
```

**已试**
1. <方法一> → <结果>
2. <方法二> → <结果>

**我的怀疑**
- <技术层面>
- <也包括：怀疑指令本身有问题，理由是……>

**请裁定**
- 是继续换方法，还是这条指令的前提就有问题？
```

第 2 条「怀疑指令本身有问题」是**必须写的可能性**。不写等于默认指令一定对。

## 4. 落盘约定

```
runtime/wa/
├── turn-001-prompt.md      # 我发给网页版 AI 的内容
├── turn-001-reply.md       # 网页版 AI 的回复原文（不改写、不摘录）
├── turn-002-prompt.md
└── ...
```

- 回复原文必须**整段落盘**，不要只存摘要——后面回溯判据、验收标准时，摘要会丢细节。
- 文件编号与 `state.turn` 一致。

---

## 5. 上下文管理与压缩

网页版 AI 的对话会越来越长。压缩规则：

| 触发 | 动作 |
|---|---|
| 对话进入明显变慢 | 把「已完成的阶段结论」整理成一段 200 字内的摘要，作为下一轮的上下文锚点 |
| 页码显示上下文将满 | 提前请它输出「当前进度 + 未决事项」清单，落盘为 `checkpoint-N.md` |
| 网页版 AI 开始记错前面的事 | 不要纠正它猜的内容，直接把它之前**自己写的**结论原文贴回去 |

**不新开对话**这条规则不因上下文变长而豁免。上下文满了由网页版 AI 侧处理（它自己的会话管理），我方只负责把关键结论落盘。
